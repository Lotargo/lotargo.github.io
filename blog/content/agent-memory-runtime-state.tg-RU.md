# Когда память агента становится частью runtime

Долговременная память AI-агента быстро перестаёт быть «блокнотом с фактами». Сначала достаточно нескольких заметок, затем их становится слишком много для постоянного prompt, появляется RAG, разделение по проектам, а после — persistent directives, которые меняют уже не знания модели, а её поведение.

**Первое важное разделение — Hot Memory и Cold RAG.**

Hot memory хранит небольшой always-on контекст: ограничения проекта, предпочтения, текущие договорённости. Cold RAG оставляет исследования, документы, решения и длинные заметки в большой библиотеке и извлекает их только по необходимости.

Идея простая: **храни много, в контекст отправляй мало**. Большое окно модели не отменяет того, что нерелевантная история создаёт шум.

Следующая проблема — scope. Память проекта A не должна случайно становиться архитектурным решением проекта B. Поэтому `all` для рабочего агента разумнее понимать как `global + current project`, а не «всё, что агент когда-либо видел».

Потом появляется более интересная граница:

`fact` — что агент знает.  
`directive` — как агент должен действовать.

«Проект использует PostgreSQL 16» — факт. «Сначала проверяй существующую архитектуру и не добавляй абстракции без причины» — уже активная конфигурация поведения.

В этот момент **persona становится runtime state**. Модель, provider и веса те же, но persistent directives могут менять автономность, формат ответов, склонность перепроверять предположения, отношение к риску и выбор стратегии в неоднозначных ситуациях.

Это не fine-tuning и не отключение встроенных safety-механизмов: более приоритетные правила платформы остаются авторитетными. Но долговременный контекст действительно способен влиять на интерпретацию запроса и выбор между допустимыми стратегиями ответа.

Отсюда появляется новая проблема: ошибочная persona тоже становится долговременной. Устаревшие предпочтения, конфликтующие directives или случайно закреплённая привычка требуют lifecycle — update, supersede, delete, scope.

**И тут возникает неожиданный побочный эффект CLI-as-Provider.**

Иногда OpenCode, Codex и другие agent CLI используют как готовый слой между своим приложением и моделью. Кажется, что путь такой:

`App → CLI → Model`

Но реально внутри CLI уже могут жить global config, plugins, MCP, skills, prompts, memory и persona. Получается **Ambient Agent State**: приложение не объявляло эти зависимости, но они всё равно меняют его поведение.

Это особенно опасно для benchmark'ов. Сравнение «Model A vs Model B» легко превращается в «Model A + моя накопленная среда vs Model B + чистая среда». Поэтому серьёзному тесту нужен clean-profile baseline.

В production вывод тот же: персональный CLI и CLI-provider лучше изолировать — отдельным HOME/config, профилем, контейнером или системным пользователем.

> **RAG отвечает, что агент знает. Persona определяет, как он использует это знание. Isolation задаёт границы, где это поведение действует.**

Именно после этой точки память перестаёт быть удобной функцией и становится частью архитектуры runtime.
