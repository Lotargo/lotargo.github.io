# Все тесты зелёные, а векторный поиск мёртв

Двое суток мой RAG-плагин искал по документам без единого вектора. Двенадцать тестовых сьютов при этом проходили успешно, бенчмарки не запускались, а пользователи ничего не замечали, потому что BM25 продолжал возвращать разумные результаты. Нашёл я это случайно — и только потому, что тестовый скрипт по ошибке импортировал не тот модуль.

![Гибридная RAG-память для AI-агентов](assets/images/memory-plugin-hero.avif "@lotargo/memory_plugin — локальная гибридная память для кодинг-агентов")

## Что за проект

`@lotargo/memory_plugin` — система долговременной памяти для AI-агентов. Она держит два слоя: заметки пользователя в Markdown и RAG-базу документов в SQLite. Поиск гибридный: BM25 через FTS5 и плотные векторы через ONNX, слитые алгоритмом relative score fusion. Всё локально, без внешних API.

Векторная половина здесь не украшение. Именно она вытягивает кросс-язычные запросы: спрашиваешь по-русски — находит в английской документации. BM25 на такое неспособен в принципе, у него нулевое лексическое пересечение.

## Как это вскрылось

Я заканчивал аудит проекта и проверял мелкий фикс в генераторе отчётов бенчмарков. Написал скрипт, который импортировал функцию рендеринга, — и вместо быстрой проверки получил полный прогон бенчмарка на ONNX. Сам по себе это был отдельный дефект: модуль запускал измерения как побочный эффект импорта.

Пока прогон шёл, я смотрел в таблицу результатов. И там было вот это:

| Стратегия | MRR@5 |
| --- | ---: |
| BM25 | 0.6706 |
| Dense Vector | **0** |
| Hybrid RRF | 0.6706 |
| Hybrid RSF | 0.6706 |

Ноль по вектору. Все двадцать одна запроса — MISSED. И, что показательнее, гибридные режимы дали ровно цифры BM25: фьюжн работал, но сливать ему было нечего.

## Причина

Эмбеддинги считались корректно — я проверил это первым делом, вызвав модель напрямую. Векторы писались в базу: 1536 байт на чанк, ровно 384 float32. Читались тоже. А вот дальше:

```js
let vecSub = r.vector;
if (typeof vecSub === "string") {
  vecSub = Buffer.from(vecSub, "base64");
} else if (vecSub.type === "Buffer" && Array.isArray(vecSub.data)) {
  vecSub = Buffer.from(vecSub.data);
} else if (Array.isArray(vecSub)) {
  vecSub = Buffer.from(vecSub);
}
if (!Buffer.isBuffer(vecSub) || vecSub.byteLength < vectorDim * 4) continue;
```

Последняя строка и убивала поиск. Движок работает на встроенном модуле `node:sqlite`, а он возвращает BLOB-колонки как `Uint8Array` — не как `Buffer`. Ни одна из трёх веток нормализации не срабатывала, `Buffer.isBuffer()` возвращал `false`, и `continue` отбрасывал строку. Каждую. Всегда.

> `Buffer` наследует `Uint8Array`, но не наоборот. Проверка `Buffer.isBuffer()` на данных из `node:sqlite` — это тихий `continue` для всей выборки.

Самое неприятное — до появления этой проверки код работал именно потому, что был проще. `Uint8Array` проваливался мимо всех веток и попадал прямо в `tempView.set(vecSub.subarray(...))`. У `Uint8Array` есть `subarray`. Всё считалось.

Проверку добавили в коммите, который назывался «await missing async calls, security fixes, and dead code cleanup». Защитная строка, написанная из лучших побуждений, отключила половину движка.

## Почему тесты молчали

Вот это интереснее самого бага.

В проекте двенадцать тестовых файлов: юнит, интеграционные, облачные. Все зелёные. Проблема в одной общей детали — каждый из них работает так:

```js
await ingestDocument({
  content: "...",
  generateEmbeddings: false,
  customDb: db,
});
```

`generateEmbeddings: false`. Сделано это осознанно и по разумной причине: тесты не должны тянуть двухгигабайтную модель и зависеть от сети. Весь прогон укладывается в 41 секунду и работает офлайн.

Но следствие такое: плотная половина движка не проверялась вообще. Единственный вызов `hybridQuery` в интеграционных тестах тоже шёл с `generateEmbeddings: false`, а в этом режиме функция сознательно переключается в `lexical_only`. То есть тест «проверки гибридного поиска» проверял BM25.

Тесты подтверждали, что векторы **записаны** — правильного размера, ненулевые. Что их кто-то потом **прочитает**, они не проверяли никогда.

## Ещё два места

Убедившись в причине, я поискал ту же ошибку по всему коду. Нашёл дважды:

- в очереди облачной синхронизации — при `hybrid-sync` в облако уходили **пустые** векторы;
- в экспорте снапшотов — снапшоты сохранялись без векторов.

Оба места повторяли ту же цепочку `if/else if` с `Buffer.isBuffer()` в конце. Обе ошибки были тихими: ни исключения, ни предупреждения в логе.

Исправление — одна функция нормализации на все три места:

```js
export function toVectorBytes(value) {
  if (value === null || value === undefined) return null;
  if (typeof value === "string") return new Uint8Array(Buffer.from(value, "base64"));
  if (value instanceof Uint8Array) return value; // покрывает и Buffer
  if (ArrayBuffer.isView(value)) return new Uint8Array(value.buffer, value.byteOffset, value.byteLength);
  if (value instanceof ArrayBuffer) return new Uint8Array(value);
  if (value.type === "Buffer" && Array.isArray(value.data)) return new Uint8Array(value.data);
  if (Array.isArray(value)) return new Uint8Array(value);
  return null;
}
```

Порядок проверок важен: `value instanceof Uint8Array` стоит до `ArrayBuffer.isView`, потому что покрывает и `Buffer`, и то, что отдаёт `node:sqlite`, без лишнего копирования.

## Что я добавил, чтобы это не повторилось

Юнит-теста на функцию нормализации мало. Он проверяет преобразование типов, но не отвечает на вопрос «а поиск-то работает?».

Поэтому появился отдельный smoke-тест с **настоящими** эмбеддингами. Он не входит в `npm test` — грузит модель, это долго. Запускается перед релизом командой `npm run smoke` и утверждает то, чего не утверждал никто:

```js
const cosines = hits.map((h) => h.cosine_sim ?? 0);
assert.ok(
  cosines.some((c) => c > 0),
  "at least one hit carries a non-zero cosine similarity — " +
  "a zero here means the dense half of the engine is dead"
);
```

Плюс кросс-язычная проверка: русский запрос должен дойти до английского документа. Это невозможно подделать лексическим поиском — если тест проходит, вектор жив.

Затем я вернул баг обратно и убедился, что тест падает. Регрессионный тест, не проверенный на воспроизведении дефекта, — это предположение, а не гарантия.

Модель тест берёт из уже существующего кэша, поэтому два гигабайта не качаются заново.

## Что я из этого вынес

**Проверки типов на границе с драйвером опаснее, чем кажутся.** `Buffer.isBuffer()` выглядит как разумная защита. На данных из `node:sqlite` это фильтр, отбрасывающий всё. Если добавляете такую проверку — сначала выясните, что драйвер возвращает на самом деле.

**Быстрые офлайн-тесты создают слепые зоны, и о них надо знать явно.** Отключить эмбеддинги в тестах было правильным решением: сорок секунд против нескольких минут, никакой сети. Ошибка не в этом, а в том, что никто не покрывал отключённую половину отдельно. У любого «пропустим тяжёлое ради скорости» есть цена — вопрос лишь в том, знаете вы о ней или нет.

**Тихая деградация хуже падения.** Упади поиск с исключением — я бы узнал через минуту. Вместо этого он вернулся к BM25 и продолжил выдавать правдоподобные ответы. Для гибридных систем это типично: запасной путь маскирует отказ основного.

**Отсутствие сигнала — тоже сигнал.** Ноль в колонке метрики не выглядит как ошибка. Он выглядит как число.

## Текущее состояние

Исправление вышло в `1.6.0` вместе с итогами аудита: девяносто два пункта по публикации, безопасности, качеству кода, тестам и документации. Свежий прогон бенчмарков дал MRR@5 0.9286 и Recall@5 100% для гибридного RSF — побайтово совпало с эталонным замером, сделанным до появления бага. Фикс вернул поведение, а не подкрутил цифры.

Пакет открыт под MIT: [npmjs.com/package/@lotargo/memory_plugin](https://www.npmjs.com/package/@lotargo/memory_plugin), исходники — [github.com/Lotargo/memory_pugin](https://github.com/Lotargo/memory_pugin).

Отдельно любопытно, что нашёл я это благодаря другому дефекту — импорт модуля запускал бенчмарк как побочный эффект. Его я тоже починил. Но не будь его, баг ждал бы следующего ручного прогона.
